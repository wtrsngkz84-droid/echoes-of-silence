# GAMEPLAY_DESIGN — 交互玩法与状态规则

> 版本：V0.9（P2 交付，配套 STORY_BIBLE V0.94 / STORY_FLOW V0.9 / PRD V0.91）
> 撰写：产品经理 / 剧情策划（队友 Qoder）
> 日期：2026-11-11
> 本文件定义全部交互玩法规则：对话与叙事呈现、手机聊天 UI、线索系统、状态变量总表、跨章状态流、结局判定矩阵、保存与重玩。逐节点台词在 STORY_SCRIPT（P3）。本文的变量名与接口形状是**给开发负责人的提案**，最终实现接口由开发负责人定稿（TEAM_ROLES §2 约定）。

## 1. 非目标（防跑偏）

- 不做自由输入对话、开放世界调查、道具合成：一切交互服务于叙事（PRD 非目标：不做 RPG 化）。
- 不做答题得分：任何「推理」环节指认错误不扣分、不卡死，只影响文案走向（防知识问答化，PROJECT_CONTEXT 红线）。
- 不模拟社交平台功能（举报/拉黑/加好友系统）：聊天 UI 只是叙事载体。

## 2. 对话与叙事呈现（FR-01/02/03）

### 2.1 节点类型与交互模型

| 节点类型 | 交互模型 | 典型 |
| --- | --- | --- |
| 固定过场 | 点击/空格推进；打字机效果（可全局设置速度） | C1-03 |
| 反应选择 | 2–3 选项 → 选内心独白或微动作文案 → 汇回主线（无客观记录差异） | C1-02/04 |
| 核心交互场景 | 专用交互组件（§3）+ 嵌入选择点 | C1-05、C2-04、C3-02、C1-08/C3-04 |
| 蒙太奇 | 多日压缩过场 + 嵌入 1–2 选择 | C1-07、C2-06 |
| 行动窗口 | 多步选择区，菜单可随日期/条件生长 | C1-09、C2-08、C3-06 |
| 章末小结 | 只读一屏 + 自动存档 | C1-10 等 |

### 2.2 对话框 UI 规格（像素风）

- 布局：底部对话框（半透明深色底 + 像素边框），说话人名字条 + 16×16 像素头像；NPC 对白白字，主角内心独白用**斜体 + 虚线边框 + 无头像**区分（FR-03）。
- 打字机效果：默认 30 字/秒，可设置「慢/标准/立即显示」；点击跳过当前句。
- 群消息与面对面对白共用文本样式表；颜色与字体规格由 ASSET_LIST 定（P4）。

### 2.3 「打字又删掉」演出规范（STORY_BIBLE §11 意象的机制化）

三主角各至少一次（对应 §11 表），演出规格统一：输入框内文字逐字浮现 → 停顿 → 逐字消隐 → 最终版定格（或留下空白）。三处固定演出：

1. 小满 C1-06：给妈妈的长文删成「妈 没事」（或「感冒」）。
2. 予安 C2-08：输入框里的「对不起」残影（12/9–12/11 动摇档）。
3. 陈屿 C3-02：整条消息的发送/删除交互（§3.4）。

### 2.4 章节切换卡

每章开始固定演出：黑屏 → 章节号 + 章名 + 「这一次，你站在｛角色名｝的位置。」→ 日期地点卡。三章句式相同，强化三视角结构（FR-06）。

## 3. 手机聊天 UI（FR-04）

### 3.1 消息流组件

- 全屏手机竖屏 UI：顶栏（群名/成员数/在线状态）+ 消息流 + 底部输入区。
- 消息单元：头像 + 昵称（群聊用 §9.6 昵称化 handle）+ 气泡 + 时间戳（关键时间戳用主题色强调：20:33、21:47、22:40）。
- 消息类型：文本 / 截图卡片（可点开放大，§3.2）/ 表情包图片 / 系统消息（「林小满 退出了群聊」）/ 时间分隔线。
- 刷屏演出：11/27 群爆段消息自动上涌（不可跳过首遍，可点击暂停/回滚查看已滚过内容）——「在洪流里找一句话」的体验即主题本身。回滚查看是必测验收点。

### 3.2 截图查看器（机制化意象「截图/裁剪」）

点击消息流中任何截图卡片 → 放大查看器：

- 完整记录类截图（EV-01）：可上下滚动查看全部消息（§5-C 原文），滚动到被公开裁掉的四条（20:31/20:36/20:58/予安 20:15）时，边缘显示**撕裂断口**视觉与一行说明「这张图被裁掉的部分」。
- 裁剪截图（EV-02）：图中仅 20:33 一条；查看器底部常驻按钮「查看完整上下文」→ 切换到 EV-01 滚动视图——**玩法语义：让玩家亲手看见被裁掉的部分**。
- 使用位置：C1-05（玩家首次收到裁剪图）、C1-07 12/2 纸条教学、C2-04（裁剪交互的对象物）、C3-02（陈屿看到的图）、S1/S2。

### 3.3 裁剪交互（第二章 C2-04 专用）

1. 呈现 §5-C 完整私聊（与 C1-04 同一数据源，逐字一致）。
2. 玩家长按任意一条消息 → 裁剪框 + 「截图」确认。
3. 选 20:31/20:36/20:58/予安 20:15 → 系统反馈「截这张，没有用」（予安内心旁白解释为什么发不出去）；试错不限次数。
4. 选 20:33 → 裁剪完成（图卡进入发送区）。
5. 配文输入框：默认显示 §5-E 文案；玩家可选更狠/删 21:52 的变体——变体以草稿层残影呈现（§2.3 演出），**发布出去的永远是 §5-E 定稿**（最终发布版规则的可视化教学）。
6. 发布确认：心跳演出（画面轻微搏动）→「发送」。

**软引导出口**（防卡死）：玩家若反复回避 20:33，三次试错后予安内心独白「就发这条。」+ 该消息高亮。设计立场：玩家被迫亲手执行裁剪是本作的核心交互命题（理解机制 ≠ 认同行为）；本设计决定标注待产品负责人最终确认（§9）。

### 3.4 输入框与「已删除的消息」（第三章 C3-02 专用）

- 输入区显示预置候选句（默认句见 STORY_FLOW C3-02；可换烈度变体 1–2 条）。
- 双按钮：发送 / 删除。
- **发送** → 进入早期发声分支：当晚被围攻段（「圣母」「他喜欢小满吧」、外号重演）→ `v_cy_early`=1。
- **删除** → 默认路径：该句存入「已删除的消息」存档——从速写本菜单可随时查看（良心账本 UI 化，§3.6）。
- C3-06 公开发声档：呈堂素材之一 = 已删除消息的截图「这是我当时删掉的」（把删掉的话发出去，与予安担责动作互为镜像）。

### 3.5 选项价格标签（第三章全菜单，红线 5 机制化）

C3-06 行动窗口每个选项旁常驻一行小字标注其代价（如「置顶围攻的可能」「要承认自己看了两周」「无公共风险，但证据将记录经手人」）。价格标签是文案，不产生新变量；其真实性由后续场景兑现（选了就有对应演出）。

### 3.6 速写本（陈屿常驻 UI）

- 章内菜单入口；显示已解锁的速写页（日期 + 教室一角 + 空椅子递增演出）与「已删除的消息」存档。
- 最后一页视结局渲染（椅子坐回 / 空着 + 小字）。

## 4. 线索与证据系统（FR-05）

### 4.1 证据库面板

- 三章各自持有面板：小满（EV-01/03/09/11 等）、予安（EV-01/02——她自己的完整记录与作案材料）、陈屿（随剧情 EV-05/04/01 + 可争取 EV-08）。
- 证据卡：编号 + 名称 + 一行简述 + 状态（已收集 / 已出示 / 已提交）。章末小结显示本章收集清单。

### 4.2 出示规则（白名单机制）

出示动作只在白名单场景可用（白名单是节点数据字段，防错位出示导致剧情崩坏）：

| 场景 | 允许出示/提交 | 效果 |
| --- | --- | --- |
| C1-08（12/4 独处） | EV-01（随敞开度=2 自动） | 陈屿知识库 +EV-01 |
| C1-09（办公室求助） | EV-03 草稿本、EV-01 完整记录、EV-11 纸条（可选提交清单） | `v_xm_help` → 2；提交物进班会处理结论文案 |
| C3-06（交证据档） | EV-01/04/05（+EV-08 若已取得） | `v_cy_act` → 2 |
| C3-06（公开发声档） | 已删除消息截图 + EV-01/04 | `v_cy_act` → 3 |
| C3-04（12/4 独处·陈屿侧） | EV-04 照片、EV-05 旁听（揭示选择） | `v_cy_reveal` |

### 4.3 推理指认（轻推理，非答题）

触发点：C2-06 树洞段子节（予安侧「帖是谁发的？」）、C3-05 公示后窗口（陈屿侧同款推理）。形式：陈列 2–3 条线索（EV-07 时间矛盾/用语重合；EV-08 预告语；排版模板关联）→ 四候选（郑晓芸 / 匿名同学 / 别有他人 / 想不出来）。

- 指认郑晓芸（正确）→ 解锁晓芸甩锅现形的预备文案（E4/班会双重追责变体）；予安侧正确指认后「问了」与「不问」的差距可视化。
- 指认错误 → 「你怀疑错了。线索还在。」不惩罚、不扣分、可再次进入；仅影响后续是否问晓芸的文案勇气差异。
- 不设倒计时、不设分数（红线：防知识问答化）。
- EV-08 的取得：陈屿线 C3-05–C3-06 间可选支线（找那位不安的女生——见 U-006 取得方式待剧本阶段细化）。

## 6. 跨章状态流规则（决策提案 P-013 核心）

### 6.1 单向流

数据只向前流动：Ch1 → Ch2 → Ch3 → 班会/结局。任何一章的代码路径不得读取「未来章」变量，不得回写「过去章」已定变量。玩家重玩某章时按 §8.3 规则处理。

### 6.2 跨章变量清单（全部）

| 写入章 → 读取章 | 变量 | 读取点 |
| --- | --- | --- |
| Ch1 → Ch2 | `v_xm_variant`、`v_xm_stay` | C2-02（私聊变体渲染）、C2-05（22:40 段渲染与群成员列表） |
| Ch1 → Ch3 | `v_xm_openness`、`v_xm_ask_cy` | C3-04（开场与请求兑现） |
| Ch2 → Ch3/结局 | `v_zy_duty`、`v_zy_ask_*` | C3-07 班会、E4 文案、晓芸甩锅段触发 |
| Ch3 → 结局 | `v_cy_act`、`v_cy_echo` 等 | 判定矩阵 |

跨章影响通过「渲染输入」实现，不做「过去章变量改写」——见 6.3。

### 6.3 回写限制与「渲染输入」原则

Ch3 的揭示行为（`v_cy_reveal`）不修改 Ch1 已写入的 `v_xm_help`；其影响以渲染输入呈现：`v_cy_reveal`≥2 时，E3/E5 班会处理结论用「多源证据版」文案（草稿本 + 完整记录 + 旁听证言 + 照片齐备），否则用「单方陈述版」。结局画面因此有真实的信息质量差异，但判定变量保持只增不改的简单性。

### 6.4 待结算请求队列

`v_xm_ask_cy` 机制：Ch1 C1-08 玩家让小满请求陈屿作证 → 场景文案停在「他说他想一想」（符合其性格）→ Ch3 在 C3-04（独处兑现）或 C3-06（行动窗口兑现）提供兑现选择；Ch3 结束仍未兑现 → 错过（结局文案如实呈现「她的请求没有等到回应」）。实现上是 1 个标记 + 2 个兑现点，无需通用队列结构。

### 6.5 最终发布版的实现约定（给开发的接口建议）

STORY_BIBLE §5 全部原文建议作为独立只读数据表（条目 id + 逐字文本 + 元数据：时间戳/说话人/引用条件），三章节点通过 id 引用呈现——引擎层面只有一份原文数据，跨章逐字一致由架构保证而非人工校对。最终接口由开发负责人定稿，DEV_HANDOFF（P6）将附完整字段建议。

## 7. 结局判定矩阵（U-002 定稿提案；配套 STORY_FLOW §8）

### 7.1 判定顺序（依次检查，首个命中即结局；判定变量仅 §5.1 的 4 个）

| 序 | 结局 | 条件 |
| --- | --- | --- |
| 1 | E5 回声 | `v_xm_help`≥2 **且** `v_zy_duty`=2 **且** `v_cy_act`≥2 **且** `v_cy_echo`=0 |
| 2 | E4 责任的重量 | `v_zy_duty`=2（且未命中 E5） |
| 3 | E3 再次求助 | `v_xm_help`≥2（且未命中 E4/E5） |
| 4 | E1 沉默的代价 | `v_xm_help`=0 **且** `v_zy_duty`≤0 **且** `v_cy_act`=0 |
| 5 | E2 及时止损 | 兜底（其余全部组合） |

### 7.2 对侧素材并入规则

- E4 命中且 `v_xm_help`≥2 → 尾声并入 E3 素材（给妈妈发消息）。

### 7.3 全覆盖与唯一性证明（验收条目 AC-FR07 的依据）

### 8.3 重玩规则（FR-09）

- 通关后解锁「从任一章开始」，两种模式：**携带重玩**（保留前章共享状态，重玩该章——刷多结局的低成本路径）与**全新开始**（全部重置，结局画廊保留）。
